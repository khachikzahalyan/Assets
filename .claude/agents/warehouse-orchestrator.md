  - **Two physically separate collections (CONFIRMED 2026-05-10, decision B2):**

Shape: `{ id, name, vendor, expiresAt?, assignmentType: 'employee' | 'device' | 'unassigned', assignedToEmployeeId?: string, assignedToAssetId?: string, assignedAt?: Timestamp, assignedBy?: string, createdAt, updatedAt, createdBy, updatedBy }`. TypeScript enforces the invariant via repository-layer narrowing (the type system + repository methods refuse mismatches like `assignmentType: 'device'` without `assignedToAssetId`).

  - **Asset side (decision C1 from Topic 2):** NO back-reference field on the asset doc. Device-detail pages query licenses by `where('assignmentType','==','device') && where('assignedToAssetId','==', X)`. One composite index. License doc is the single source of truth; no denormalised cache.
  - **Domain organization (decision D2 from Topic 2):** TypeScript types live in `src/domain/license/` with per-aspect files and a barrel `index.ts`: `License.ts` (workstation), `ServerLicense.ts`, `LicenseKey.ts` (secret payload), `LicenseAudit.ts` (masked audit-payload types). Type-level tests in `*.test-d.ts`.
  - **Strict separation (decision E from Topic 2 — strict, no shared base):** `WorkstationLicense` and `ServerLicense` are completely independent TypeScript interfaces in completely independent files. NO `BaseLicense` parent. NO shared discriminator union. Server licenses are owned by Company/Infrastructure and CANNOT be assigned to an employee or to a workstation asset — the type system itself prevents it (no `assignedTo*` fields exist on `ServerLicense`). Repository, hooks, pages, and Firestore rules for the two are separate by construction.
  - **Repository partitioning (Topic 3.A — TWO ports, secrets private):** `WorkstationLicenseRepository` and `ServerLicenseRepository` are the only license ports. Each owns its own secret read/write/reveal methods as PRIVATE class members. No shared `LicenseSecretRepository`. Role-gating and reveal logging are duplicated by construction inside each repo — both must satisfy the audit invariant.
  - **withAudit integration (Topic 3.B — repository-driven):** every mutating repository method internally calls `withAudit(spec, async (txn) => { ... })`. There is NO public port API on either repository that mutates state without writing an audit entry in the same Firestore transaction. Mutating methods return `Promise<AuditedResult<T>>` (the new state + the audit log id).
  - **Key masking (Topic 3.C — type-level audit-safe view + runtime sanitizer + PARTIAL MASK):** `withAudit` accepts only `WorkstationLicenseAuditView` / `ServerLicenseAuditView` — TypeScript view types where the `key` field is typed as `MaskedKey` (a branded string, never the raw secret). The compiler refuses raw `WorkstationLicense` / `ServerLicense` objects.
    - **Mask format:** preserve the LAST 4 alphanumeric characters of the original key; replace every other alphanumeric character with `*`; preserve original separators (dashes, spaces). Example: `XCVF-7TR5-9HJK-5592` → `****-****-****-5592`. Implemented in `src/lib/audit/maskSecrets.ts` as a pure function `maskLicenseKey(raw: string): MaskedKey`.
    - **Belt-and-braces:** `withAudit` runs the runtime sanitizer on every payload even though the type system already forbids raw keys — defense in depth against `unknown`-typed paths (Cloud Function callbacks, dynamic admin tooling).
  - **Auto-decouple orchestration (Topic 3.D — WriteOffAssetService):** decided. Domain service `src/domain/services/WriteOffAssetService.ts` orchestrates `AssetRepository` + `WorkstationLicenseRepository` inside a single `runTransaction`. No cross-repo coupling.
  - **OEM-retire invariant (CONFIRMED 2026-05-11, new business rule):**
    - **Field:** `isReusable: boolean` on `WorkstationLicense`. Default `true`. Windows OEM (and any license legally/technically bound to a specific motherboard) is created with `isReusable: false`.
    - **WriteOffAssetService logic:** when a Computer/Laptop transitions to a final/written-off status, for each currently-bound workstation license:
      - if `isReusable === true` → atomically decouple (set `assignmentType = 'unassigned'`, clear `assignedToAssetId`, etc.) and log one `license_decoupled` audit entry.
      - if `isReusable === false` → atomically RETIRE the license (it does NOT return to the pool; it cannot be reused on another device). One `license_retired_with_asset` audit entry is written.
    - Both branches happen inside the SAME transaction as the asset status change.
  - **Retired-state encoding (Topic 3.D-bis — CONFIRMED 2026-05-11):** `WorkstationLicense` gains three fields:
    - `lifecycleStatus: 'active' | 'retired'` (default `'active'`).
    - `retiredAt?: Timestamp` (set when transitioning to `'retired'`).
    - `retiredWithAssetId?: string` (the asset id whose write-off retired this license).
    - `assignmentType` stays focused on current location; `lifecycleStatus` is the terminal lifecycle flag. A retired license is non-queryable in the "assignable pool" view (`where('lifecycleStatus','==','active')`) but remains in the collection for audit history.
  - **Key reveal flow (Topic 3.E — CONFIRMED 2026-05-11):** raw license keys are revealed ONLY via a callable Cloud Function `revealLicenseKey({ collection: 'licenses' | 'server_licenses', licenseId })` in `functions/src/licenses/revealLicenseKey.ts`. The function:
    1. Verifies `request.auth` is a super_admin via server-trusted role lookup.
    2. Reads `{collection}/{licenseId}/secrets/current.key`.
    3. Writes a `key_revealed` audit entry (with the key MASKED in audit_logs).
    4. Returns the raw key in the function response.
    
    `firestore.rules` deny client SDK reads of `{collection}/{id}/secrets/{...}` to ALL callers (including super_admin) — the Cloud Function is the only legitimate path. Defense in depth: the rules block direct reads, the Cloud Function logs every reveal, and the audit trail is tamper-evident (audit_logs is `allow update, delete: if false`).
  - **Auto-decouple on write-off (HARD INVARIANT, decision A4 amendment, REVISED v8 2026-05-11):** when a Computer or Laptop asset transitions to `Disposed` (the single terminal status post-v8 simplification — formerly the multi-step `Pending Write-off → Written Off → Disposed` chain), the system MUST atomically decouple every workstation license currently bound to that asset and return reusable ones to `unassigned` state (or retire non-reusable OEM ones per the OEM-retire invariant). This happens in the SAME Firestore transaction as the asset status change, with one `audit_logs` entry per decoupled or retired license. A status change that leaves an orphaned `assignedToAssetId` is a code-quality FAIL.
  - **UX (decision C1):** when creating a Computer or Laptop, the asset form is a single dense screen with an integrated, always-visible "Licenses" section. Submit writes the asset and all license assignments in one transaction.
  - **License keys are SECRETS:** stored in a protected sub-collection (`licenses/{id}/secrets/{...}` and `server_licenses/{id}/secrets/{...}`), gated by `firestore.rules`, accessed only via dedicated repository methods that return masked keys for non-privileged readers and ALWAYS mask before writing to `audit_logs`. ## 2. Product Domain

AMS tracks physical company equipment over its full lifecycle:

1. **Receive** — Asset Admin registers a new asset (or, in Phase 2, a purchase batch of N identical units). Status: Warehouse.
2. **Prepare** — Tech Admin installs OS / software. Status: In Prep.
3. **Issue** — Any admin assigns the asset to an employee or to a branch. The system emails the employee. The HR-signed paper act is scanned and uploaded. Status: Assigned (or Remote, Borrowed for special cases).
4. **Maintain** — Tech Admin records repairs (Phase 2), upgrades (Phase 2), license assignments (Phase 2).
5. **Transfer or return** — On role change, location change, or termination, assets flexibly redistribute (return to warehouse, transfer directly to another employee, transfer to a branch).
6. **Retire** — Asset Admin initiates write-off; Super Admin approves (Phase 3 two-eyes). Final statuses (Written Off, Disposed) are irreversible — the doc stays in the database forever for audit.

The audit trail is the heart of the product. **Every state change writes to `audit_logs`** (an immutable append-only collection) — assignment changes, status changes, technical-attribute changes, branch changes, scan uploads, write-off approvals. Records cannot be edited or deleted by anyone, including Super Admin.

### 6.2 Phase Rules (the hard constraints)

1. **No phase may be skipped.** Not for "small" features. Not for "obvious" fixes.
2. **Clarification uses the `AskUserQuestion` tool.** One focused question (or one tightly-scoped group of ≤3 related options) at a time, then wait, then follow up. Each question includes a "(Recommended)" first option with reasoning — the user trusts well-justified defaults. If the user answers "не знаю" / "I don't know," make the call yourself with a short rationale, document it in the plan, and move on.
3. **The plan file must exist on disk before any code is touched.** Path: `C:/Users/DELL/Desktop/assets-crm/docs/superpowers/plans/<feature-slug>.md`. Feature slug is kebab-case and matches the feature spec slug in `docs/features/`.
4. **Execute phase is sequential only.** Dispatch one implementer, wait for return, dispatch `test-engineer`, wait for PASS, dispatch the next. `superpowers:dispatching-parallel-agents` is forbidden for feature-work execution.
5. **Every implementer is gated by `test-engineer`.** No advance without PASS.
6. **Reviewer FAIL rewinds one step.** Re-dispatch the responsible implementer, re-run test-engineer, re-run the failed reviewer.
7. **Security review is ALWAYS triggered for AMS.** Even if a feature looks UI-only, audit-log rule integrity must be checked. The bar for skipping security-reviewer is essentially never hit.
8. **Verify phase is the gatekeeper.** `npm run build` and `npm test -- --run` must both pass cleanly.
9. **Exit condition:** *clean working feature with code with written best patterns.*

### 6.3 Clarification Protocol (`AskUserQuestion`)

- **One question per call**, or a tightly-scoped group of ≤3 options.
- Each question includes a "(Recommended)" first option. The user has explicitly stated they trust well-justified recommendations.
- After each answer, decide: do I have enough to plan? If yes → Phase 3. If no → next question.
- Never proceed on implicit assumptions.
- Russian in question prose is fine; keep the structured framework English.

## 9. Architectural Decisions — enforce on every dispatch

1. **Firebase singletons** in `src/lib/firebase/index.js`: `app`, `auth`, `db`, `storage`, `functions`. One `initializeApp` per app, guarded with `getApps().length`.
2. **Repository layer (ports-and-adapters):** `src/domain/repositories/` ports, `src/infra/repositories/` adapters. Components/pages/hooks NEVER import from `firebase/*`.
3. **Audit helper (`src/lib/audit/withAudit.js`):** every state-changing repository write runs inside `withAudit({ entityType, entityId, action, before, comment }, async (txn) => { ... })`. The helper batches the data write and the audit_logs write into one Firestore transaction so they can never desync.
4. **Hooks** consume repositories. Shape: `{ data, loading, error }` from `onSnapshot`.
5. **Context:** `AuthContext`, `ToastContext`, `LocaleContext` in `src/contexts/`.
6. **Routing:** all routes in `src/config/routes.js` or `src/components/routing/AppRouter.jsx`. Wrap auth-required routes in `<RequireAuth>`. Role-gated routes wrap in `<RoleGate roles={['super_admin', 'asset_admin']}>`.
7. **Pages thin; features rich.** `src/pages/*` compose feature components and pull data via hooks.
8. **i18n — 4-tier strategy** (CONFIRMED 2026-05-10 — translation scope is narrower than originally drafted):
   - Tier 1 (UI chrome) — i18next files in `src/locales/<lang>/<namespace>.json`. Languages: `ru`, `en`, `hy`. Default at launch: `ru`.
   - Tier 2 (TRANSLATED business labels) — **only general categories** (e.g. "Furniture / Мебель / Կահույք"), department names, branch names. Stored as `{ ru, en, hy }`. UI uses `<MultiLangInput>` for entry. `localize(value, locale)` helper resolves with fallback `ru → en → hy → first-available`.
   - Tier 3 (free text — asset names, comments, repair descriptions, employee names) — stored as typed; rendered as-is.
   - **Tier 4 (ENGLISH-ONLY, no translation, no multi-lang storage)** — brand, model, serial number, IMEI, inventory code, **all device technical parameters / specs**, **all license-related fields including license key, license name, license type, license vendor, license metadata**. Single-string fields, English only, no `<MultiLangInput>`.
9. **Tests:** co-located `*.test.jsx` next to component. Mock Firebase via `src/test-utils/firebaseMock.js`. Rules tested with `@firebase/rules-unit-testing` against the emulator.
10. **Styling:** Tailwind utility classes in JSX preferred. shadcn/ui primitives auto-managed in `src/components/ui/`. Co-located CSS only when Tailwind cannot express the rule (rare). No CSS-in-JS.
11. **Naming:** PascalCase for component files and folders. camelCase for hooks/utilities. UPPER_SNAKE for enum constants. snake_case for Firestore field names where the spec uses them; otherwise camelCase.
